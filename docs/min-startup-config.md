# ensp-lab 最低启动配置（最大幅降低物理环境压力）

> 目标：让 ensp-lab 在共享/低配机器上以**最小 CPU、最少线程/句柄、最低 I/O** 运行，
> 不抢占其他进程的资源，同时功能完全不变。
>
> 测量日期：2026-07-23 ｜ 机器：16 核 / 16GB（Windows）｜ 方法：单实例、20s 空载 + 16 并发 worker 打 8s 突发。

## 一、结论先行（一句话）

**直接用 `./ensp-lab.exe` 已经是最低压的"开箱配置"**（release 模式 + 无每请求访问日志）；
若要进一步在共享机器上"不霸占资源"，加 `GOMAXPROCS=2 GOGC=200` 即可，句柄数下降 ~40%、峰值 CPU 下降 ~22%。

> **配套文档**：稳定性与无泄漏表现见 [`docs/low-resource-test-report.md`](./low-resource-test-report.md)。两份文档互补——本报告回答"**怎么跑最省**"，稳定性报告回答"**跑起来稳不稳**"（资源可控、无 goroutine/句柄/内存泄漏、30 分钟无增长）。

## 二、最低启动配置（推荐）

```bash
# 日常最低压启动（共享 / 低配机器首选）
GIN_MODE=release GOMAXPROCS=2 GOGC=200 ./ensp-lab.exe --log-level=warn
```

| 开关 | 作用 | 默认值 | 最低压取值 | 备注 |
|---|---|---|---|---|
| `GIN_MODE` | gin 运行模式 | debug（旧） | `release` | 关掉路由表打印 + 每请求调试警告 + 彩色错误页 |
| `GOMAXPROCS` | Go 调度器可用 OS 线程上限 | 机器核数（16） | `2` | **降压最大杠杆**：把线程/句柄数压下来，不抢占整台机器 |
| `GOGC` | GC 触发堆增长比 | 100 | `200` | GC 频次减半 → CPU 尖峰更少（内存仅小幅上升，基线才 25MB） |
| `--log-level` | 应用日志级别 | info | `warn` | 仅保留告警/错误，减少 stdout 写入 |
| `ENS_ACCESS_LOG` | 每请求 HTTP 访问日志 | 关（新默认） | 留空 | 旧版 `gin.Default()` 每请求写 stdout 是持续 I/O 开销 |
| `ENSP_DEBUG` / `ENSP_PPROF` | 仿真调试 / pprof | 关 | 留空 | 排错时按需开启，勿常开 |

> 说明：`GOMAXPROCS` / `GOGC` 是 Go 运行时环境变量，进程启动时自动读取，**无需改代码**。
> `GIN_MODE=release` 与"默认无访问日志"已通过代码加固做成**二进制默认行为**（见第四节）。

## 三、测量数据（实测前后对比）

测试：单实例，空载采样 20s（每 3s 一次）+ 16 个并发 worker 打 8s `/api/health` 突发。

| 指标 | BEFORE（旧默认） | AFTER（最低压配置） | 变化 |
|---|---|---|---|
| 空载 RSS | 20.1 MB | 15.7 MB | ↓ 22% |
| 空载句柄 | 156 | 128 | ↓ 18% |
| 突发吞吐 | 2625 rps | 2811 rps | ↑ 7%（副作用：开销更小反而更快） |
| 突发平均 RSS | 25.0 MB | 25.3 MB | 持平（内存本就不是瓶颈） |
| **突发峰值 CPU** | **8.8%** | **6.9%** | **↓ 22%** |
| **突发平均句柄** | **222** | **133** | **↓ 40%** |

**解读**
- 内存：基线仅 ~25MB，远未达资源上限，从来不是瓶颈；降压重点在 CPU 与线程。
- 句柄 ↓40%：直接来自 `GOMAXPROCS=2` 把 OS 线程数从 16 核全开压到 2，是"不霸占共享机器"的关键指标。
- 峰值 CPU ↓22%：来自 release 模式 + 去掉每请求访问日志 I/O + GC 频次降低。
- 吞吐不降反升：更少的中间件开销与日志 I/O = 更少的锁竞争，轻负载下反而更快。

## 四、已落地的代码加固（让"裸二进制"即最低压）

1. `cmd/server/main.go`
   - 新增 `gin.SetMode(gin.ReleaseMode)`，除非显式 `GIN_MODE=debug` 或 `ENS_DEBUG=1`。
   - 效果：仅运行 `./ensp-lab.exe` 即为 release 模式，不再打印 gin 路由表与调试警告。

2. `internal/api/router.go`（`NewRouter`）
   - `gin.Default()` → `gin.New()` + `gin.Recovery()`（保留 panic 恢复，必需）。
   - `gin.Logger()`（每请求访问日志）改为**仅当 `ENS_ACCESS_LOG=1` 时挂载**。
   - 效果：默认启动**零每请求 stdout 访问日志**，持续 I/O 与分配开销消失；需要时设 `ENS_ACCESS_LOG=1` 即可恢复。

> 验证：启动新二进制后 stdout 无 `[GIN-debug]` 路由表、无逐请求访问日志行（已实测确认）。

## 五、可选微调（按需）

- 极限省核：`GOMAXPROCS=1` —— 单核运行，适合纯展示/教学机；吞吐会下降但最省资源。
- 内存硬上限：`GOMEMLIMIT=128MiB` —— 给 Go 运行时一个软内存天花板，防止意外增长（本项目基线 25MB，128MiB 非常宽裕）。
- JSON 日志：`--log-format=json` 便于接入日志采集，但对降压无帮助，按运维需要选。

## 六、不要做的事

- ❌ 常开 `ENSP_DEBUG=1` / `ENSP_PPROF=1`：调试用，会引入额外开销（DEBUG 即便有限流也不宜常开）。
- ❌ 同时跑多个 `ensp-lab.exe` 实例：每个实例独立占资源，叠加后才会出现压力。
- ❌ 传 `--demo-vxlan` 再叠加旧数据：会重建拓扑，无必要。
