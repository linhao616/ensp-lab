# ensp-lab 团队与 AI 协同工作台 · 项目协作规范

> 适用范围：所有参与 `ensp-lab`（华为 eNSP 网络仿真实验平台）项目的人员，包括**开发者**与 **AI 助手**。
> 文档目标：明确角色分工、协作流程、沟通格式、代码提交流程与问题反馈/修复流程，让"人提需求、AI 出活、人审查、人验收"形成稳定闭环。

---

## 一、文档用途

本文档面向所有参与 ensp-lab 项目的人员（开发者 + AI 助手），明确以下内容：

- 团队与 AI 的**角色分工**
- 端到端的**协作流程和规范**
- 团队与 AI 之间的**沟通方式和指令格式**
- **代码提交流程**（生成 → 自测 → 审查 → 验收 → 合并）
- **问题反馈和修复流程**（Bug 流转闭环）

---

## 二、核心原则

### 1. 角色定义

| 角色 | 职责 | 负责方 |
| --- | --- | --- |
| 产品经理 | 定义需求、优先级、验收标准 | 团队 |
| 架构师 | 技术决策、架构演进 | 团队 + AI |
| 开发工程师 | 核心代码实现、测试 | 团队 + AI |
| AI 助手 | 代码生成、重构、测试、文档 | AI（WorkBuddy） |
| 代码审查者 | 审查 AI 生成的代码 | 团队 |

### 2. 协作流程

```
团队提出需求 → AI 生成代码/方案 → 团队审查 → 反馈修改 → AI 优化 → 验收合并
```

### 3. 分工边界

- **团队负责**：需求定义、架构决策、关键路径设计、代码审查、最终验收。
- **AI 负责**：代码实现、重构、单元测试、文档生成、Bug 修复、优化建议。
- **共同负责**：技术方案讨论、代码走查、问题定位。

> 原则：**AI 不替代最终决策权**。需求是否做、架构怎么走、代码能不能合并，最终由团队拍板；AI 提供可审查的实现与依据。

## 三、沟通规范

### 1. 需求描述格式

```
【目标】要实现什么
【背景】为什么需要
【约束】有什么限制（技术栈、时间、资源）
【期望】预期的交付结果
```

> 示例
> ```
> 【目标】支持 VXLAN 隧道拓扑的一键创建
> 【背景】当前手动搭建 VXLAN 实验耗时且易错
> 【约束】沿用现有 ns-x 引擎，Go 1.26+，本周内出可用版本
> 【期望】新增命令可生成 Spine-Leaf + VXLAN 配置，并通过本地验证
> ```

### 2. 反馈格式

```
【问题】具体哪里有问题
【期望】希望改成什么样子
【优先级】P0 / P1 / P2
```

### 3. 验收标准

- ✅ 代码通过 `go build` 和 `go test`
- ✅ 功能在本地验证通过
- ✅ 符合项目编码规范（见第四节与 `gofmt` / `go vet`）
- ✅ 相关文档已更新

## 四、文件组织规范

```
ensp-lab/
├── cmd/                 # 可执行程序入口
├── internal/            # 内部包（不对外暴露）
│   ├── api/             # Gin handlers（含 validation.go 集中输入校验）
│   ├── sim/             # 仿真引擎（engine_nsx.go / gont_emulator.go）
│   ├── topology/        # 拓扑数据模型
│   ├── router/          # gont FRR 配置写入与同步
│   ├── storage/         # 文件 / 内存存储
│   ├── cli/             # 仿真 VRP 解析器（无 shell 执行）
│   ├── metrics/         # 常驻指标采样
│   └── protocol/        # 协议模拟器
├── pkg/                 # 公共包（可对外引用，按需新增）
├── frontend/            # React 前端源码
├── web/dist/            # 前端构建产物（通过 embed.go 嵌入二进制，按需新增）
├── docs/                # 文档目录
│   ├── ensp-lab_manual.md        # 产品手册
│   ├── COLLABORATION_GUIDE.md    # 协作规范（本文件）
│   └── vxlan-topology-plan.md    # 拓扑规划
├── archive/             # 已归档的旧代码
├── go.mod
├── go.sum
├── README.md            # 项目简介
├── PROJECT_SNAPSHOT.md  # 项目快照
└── ROADMAP.md           # 路线图
```

> 说明：`pkg/`、`web/dist/` 为本规范约定的目标目录；当前仓库已落地 `cmd/`、`internal/`、`frontend/`、`docs/`、`archive/`。新增对外包请放入 `pkg/`，前端产物请放置 `web/dist/` 并通过 `embed.go` 嵌入。

**编码规范要点（来自项目实践）**

- 所有外部输入必须经 `internal/api/validation.go` 校验（TopoID 正则、设备类型枚举、Ident·Name 拒控制字符、`net.ParseIP`/`ParseCIDR`、OSPF Area、ASN、Finite、TopologyPayload）。
- FRR 配置注入防护：`applyOSPFConfig`/`applyBGPConfig` 必须校验 CIDR / Area / ASN / 邻居 IP。
- 数据竞争防护：`updateTopology`/`updateDevice` 必须深拷贝（`t.Clone()` / `updated := *existing`）后再绑定 JSON。
- 前端输出转义：`CliTerminal.tsx` 经 `escapeHtml`，勿移除转义逻辑。
- 提交前务必执行 `go fmt ./...`、`go vet ./...`、`go build ./...`、`go test ./...`。

## 五、AI 指令约定

### 1. 标准指令模板

```
【任务类型】代码生成 / 重构 / 测试 / 文档 / Bug修复 / 优化
【具体内容】要做什么
【涉及文件】需要修改哪些文件
【验证标准】如何确认完成
```

### 2. 优先级标识

| 标识 | 级别 | 含义 |
| --- | --- | --- |
| 🔴 P0 | 阻塞 | 阻塞性，必须立即修复 |
| 🟠 P1 | 重要 | 影响用户体验，需尽快处理 |
| 🟡 P2 | 一般 | 一般问题，后续迭代处理 |
| 🟢 P3 | 优化 | 优化类，有时间再处理 |

### 3. 常用指令速查

| 场景 | 示例 |
| --- | --- |
| 生成代码 | "请生成一个创建 VXLAN 拓扑的函数" |
| 修复 Bug | "请修复 `dis ip int` 命令参数解析失败的问题" |
| 优化性能 | "请优化 `engine_nsx.go` 中的转发性能" |
| 生成测试 | "请为 `engine_nsx.go` 生成单元测试" |
| 更新文档 | "请更新 `PROJECT_SNAPSHOT.md` 的 API 端点表格" |
| 代码审查 | "请审查 `internal/api/router.go` 的改动" |

## 六、代码提交流程

### 1. AI 生成代码后

```
AI 生成 → AI 自测（go build / go test）→ AI 输出变更说明
        → 团队审查 → 团队反馈 → AI 修复 → 合并
```

- AI 每次交付应附带**变更说明**：改了哪些文件、为什么改、如何验证、是否有回归风险。
- 团队审查要点：需求符合度、架构一致性、安全约束（输入校验 / 注入防护 / 数据竞争）、测试覆盖。
- 合并前必须全部通过验收标准（第三节第 3 条）。

### 2. 提交信息规范

采用 Conventional Commits 风格：

```
feat:     新增 VXLAN 隧道支持
fix:      修复 dis ip int 参数解析失败
docs:     更新 API 文档
test:     增加集成测试覆盖
refactor: 重构 engine 接口
```

> 推荐结构：`<type>: <简明主题>`；需要时在空行后补充正文（动机、影响范围、关联 Issue）。

## 七、问题反馈流程

发现 Bug 时，按以下格式反馈（越结构化，AI 越能精准定位）：

```
【问题现象】XXX
【复现步骤】1. 2. 3.
【预期结果】XXX
【实际结果】XXX
【环境信息】OS / Go 版本 / 提交 ID
【优先级】P0 / P1 / P2
```

**流转闭环**

1. 团队发现 Bug → 按上述格式提交 Issue，标注优先级并关联原需求 / PRD / 测试用例。
2. AI 定位问题 → 修复代码 → 生成回归测试（覆盖原问题 + 边界场景）。
3. 团队验证修复 → 确认无回归 → 更新 Issue 状态 → 合并。
4. 修复说明须包含：根因依据、改动点、影响范围、回归结论。

> 原则：**不在证据不足时断言根因**；对代码 / 日志 / 接口问题的判断需标注依据。涉及线上事故时，优先确认影响范围、止损方案与回滚预案。

## 八、团队与 AI 协作示例

### 示例 1：新增功能

```
团队：定义需求 → 输出需求文档
AI  ：生成代码 → 生成测试 → 更新文档
团队：审查代码 → 验证功能 → 合并
```

### 示例 2：修复 Bug

```
团队：发现 Bug → 提交 Issue
AI  ：定位问题 → 修复代码 → 生成测试
团队：验证修复 → 确认无回归 → 合并
```

### 示例 3：技术讨论

```
团队：提出问题 → 讨论方案
AI  ：提供方案 → 代码示例
团队：决策 → 确认实施路径
AI  ：实施 → 交付
```
